# ADR 016 — Palette de couleurs globale de la plateforme (`platform_config`)

- **Statut :** Accepted (confirmé le 2026-11-21 par la responsable technique : condition remplie par le code, voir la décision en fin de document) ; initialement Accepted **avec condition** (2026-11-09, décision de la responsable technique par délégation) : la palette et le logo étaient modifiables pour toute la plateforme par n'importe quel owner ou admin d'organisation ; **avant tout client réel (au plus tard J54), l'écriture est restreinte aux administrateurs de la plateforme** (`private.is_platform_admin`). **Condition mise en œuvre le 2026-11-18** (migration `20261214100000`, voir « Note de mise en œuvre ») : **changement à valider par la responsable technique**
- Date : 2026-11-07
- Sources : spec §6, §11 ; ADR 005 (isolation, §10 Platform Admin), ADR 007 (modèle de données), ADR 014 (RBAC), ADR 015 (kit UI).
- Historique : (1) `master_config`, palette par organisation : abandonnée avant tout commit, car la page de connexion ne connaît aucune organisation ; (2) palette globale éditée par un « administrateur de la plateforme » (table `platform_admins`) : abandonnée, car le rôle Platform Admin est prévu au J14 dans le schéma `private` (ADR 005 §10) et le propriétaire du produit veut que les owner/admin règlent les couleurs.

## Contexte
Le propriétaire veut choisir les couleurs de l'application et les retrouver partout, y compris sur la page de connexion, quel que soit le navigateur. Une palette par organisation est impossible avant la connexion : la palette est donc **globale**.

## Décision
1. **`public.platform_config`** (`key` PK, `value jsonb`, `updated_by`, horodatages). Donnée **globale, non tenant** : pas d'`organization_id` (exception documentée dans `900_schema_lint.test.sql`, comme `plans`). Liste blanche de clés (`appearance.palette`) et formes contraintes par `CHECK` (objet jsonb ≤ 16 Ko).
2. **Aucun droit direct** sur la table (anon, authenticated, service_role) ; RLS activée sans politique.
3. **Écriture** : `public.set_platform_config` / `reset_platform_config` (wrappers `SECURITY INVOKER` → `private.*` `SECURITY DEFINER`, `search_path` vide), réservées aux **administrateurs de la plateforme** (`private.can_manage_platform_config()` = `private.is_platform_admin()`, d'après `auth.uid()` et `private.platform_admins`, jamais `user_metadata`). Version d'origine (jusqu'à la migration `20261214100000`) : tout owner ou admin actif d'au moins une organisation. La base valide la forme (modes `light` / `dark`, jetons de la liste blanche, couleurs `#rrggbb` en minuscules) ; l'application (`packages/domain/src/theme`) ajoute le contraste WCAG AA (4,5:1) sur six paires texte/fond.
4. **Lecture** : `public.get_platform_config(p_key)`, exécutable par **`service_role` seulement**, appelée côté serveur par `apps/web/lib/service/platform-config.ts` (module de `lib/service/**`, seul emplacement autorisé pour `createAdminClient`). `anon` n'obtient aucun droit : les règles de lint L4 / L11 restent intactes. La valeur est re-validée (`paletteSchema`) avant d'être transformée en CSS.
5. **Rendu** : `paletteToCss` (hex uniquement) est injecté par le layout de locale dans toutes les pages (connexion, inscription, invitation, application). Aucune chaîne libre n'atteint le CSS.
6. Pages `/settings/appearance` et `/settings/logo` et lien « Paramétrage » : administrateurs de la plateforme (`can_manage_platform_config`) ; un owner / admin d'organisation qui ouvre l'URL voit un message en lecture seule (ar / en / fr), sans éditeur ; la base revérifie à l'écriture.

## Conséquences et risques
- **Risque assumé** : la palette est unique pour toute la plateforme ; **l'owner ou l'admin de n'importe quelle organisation la modifie pour tous les clients**. À réévaluer avant l'ouverture à de vrais clients (remplacer par le Platform Admin du J14, ou par une palette par organisation après connexion).
- **Extension du périmètre de `service_role`** : `admin.ts` ne servait qu'à la limitation de débit ; il lit maintenant aussi une donnée globale non sensible (une palette). Aucune donnée d'organisation n'est lue. À valider.
- Lecture à chaque rendu (une requête RPC par page) : acceptable en développement ; un cache court est à prévoir si la charge l'exige.
- Les jetons non modifiables (`border`, `muted`, `input`, `destructive-text`) gardent leurs valeurs ; `card`, `popover` et la barre latérale suivent `background` / `foreground`. Le dégradé de marque des pages publiques reste fixe.
- Un appel direct à la fonction SQL par un owner/admin contourne la vérification de contraste (la base ne la connaît pas). Accepté.
- Journal d'audit : non branché (table non tenant ; organisation d'accueil des lignes à décider avec la PR J12).
- **Logo** (clé `appearance.logo`, migration `20261114110000`) : `{ "mime", "data" (base64) }` dans `platform_config`, mêmes droits que la palette. PNG / JPEG / WebP seulement (**SVG refusé** : script possible), type reconnu par les **octets de signature** (validé par zod ET par `private.is_valid_logo`), ≤ 128 Ko décodés. Servi par `GET /api/brand/logo` (type DÉTECTÉ, `nosniff`, CSP `default-src 'none'; sandbox`), URL versionnée par `updated_at` (`get_platform_config_updated_at`, service_role) ; le composant `Brand` lit l'URL dans un contexte fourni par le layout de locale. Un logo énorme n'est jamais accepté ; la valeur jsonb est plafonnée à 200 000 octets pour cette clé (16 Ko pour la palette).
- Retour arrière : `supabase/rollbacks/20261114110000_platform_logo.sql` puis `20261114100000_platform_config.sql` (supprime palette et logo).
- Suite (J14) : le rôle Platform Admin existe maintenant (`private.platform_admins`). Restreindre la palette et le logo aux administrateurs de la plateforme reste possible (remplacer `can_manage_platform_config` par `is_platform_admin`) : décision en attente, comportement actuel inchangé (owner/admin d'organisation).

## Note de mise en œuvre (2026-11-18) — condition levée
- **À valider par la responsable technique** : qui peut écrire la palette et le logo passe de « owner / admin d'une organisation » à « administrateur de la plateforme ». La **matrice RBAC de l'ADR 014 et `packages/permissions` ne changent pas** : la palette et le logo n'y figurent pas, le Platform Admin n'est pas un rôle d'organisation (comme le SMTP et l'administration des plans). La restriction vit hors matrice, dans la base (`private.is_platform_admin`).
- Migration `20261214100000_platform_config_admin_only.sql` : seule `private.can_manage_platform_config()` change (`select private.is_platform_admin()`) ; `set_platform_config` / `reset_platform_config` l'appellent avant toute validation. Retour arrière : `supabase/rollbacks/20261214100000_platform_config_admin_only.sql` (rétablit le risque assumé ci-dessus). Aucune donnée touchée.
- Garde en trois endroits : base (42501), Server Actions (`forbidden`), UI (menu masqué, page en lecture seule). Lecture publique (`GET /api/brand/logo`, rendu de la palette) inchangée.
- Conséquence opérationnelle : sans ligne dans `private.platform_admins`, personne ne peut régler la palette ni le logo ; ajout par SQL (runbook `plans-quotas.md`). En local, seul le compte seed `shared@seed.test` l'est.
- Reste ouvert : palette par organisation après connexion (non décidé) ; page SMTP toujours en redirection pour les non-administrateurs.

## Décision de la responsable technique (2026-11-21)
- **Validé** : la palette et le logo ne sont modifiables que par les **administrateurs de la plateforme** (garde en base et sur le serveur, migration `20261214100000`). La matrice de l'ADR 014 reste inchangée (ressource hors matrice, comme le SMTP et l'administration des plans).
- **Reste à faire avant le premier client réel** : enregistrer l'administrateur de la plateforme sur la base hébergée (runbook `hosted-database.md`, section 6) ; sans cela, personne ne peut régler la palette ni le logo.
