# Checkpoint C1 — Audit de conformité Phase 1 (gate G1)

- **Date :** J15 (mar 1 déc 2026, préparé en avance le 7 nov 2026)
- **Périmètre :** Phase 1 « Fondations » (J4 à J15) : noyau tenant, RLS, authentification, organisations, membres et invitations, couche service, audit, jobs et worker, plans et quotas, Paramétrage (palette, logo, SMTP).
- **Condition de GO (plan §1) :** test d'isolation de deux entreprises réussi sur l'interface, l'API, la RLS et le worker (spec §13-1) ; rôles disponibles (spec §13-2) ; audit sans écart bloquant.
- **Recommandation de l'ingénieur·e : GO avec réserves** (§5). La décision de GO / NO-GO appartient à la responsable technique.

## 1. Preuve de l'isolation (critère §13-1)
Scénarios `tests/acceptance` (`pnpm test:e2e`, 35 tests, pile locale réelle) :

| Couche | Ce qui est prouvé | Fichier |
|---|---|---|
| RLS / API (Data API réelle) | Pour 7 profils (dont `shared`, owner d'Alpha et sales agent de Beta), toute table tenant ne renvoie que des lignes de leurs entreprises ; un filtre sur l'identifiant de l'autre entreprise ne révèle rien ; anonyme et compte sans adhésion ne voient rien. Les tables tenant sont **découvertes dans le catalogue** : une table ajoutée plus tard est couverte sans modifier le test. | `t1-isolation.test.ts` |
| RLS / API, écritures | Modifier, supprimer, insérer chez l'autre entreprise ou y déplacer une ligne est refusé ; l'utilisateur à deux rôles écrit chez Alpha (owner) mais pas chez Beta (sales agent). | `t1-isolation.test.ts` |
| Worker (file de jobs) | 3 jobs par entreprise : chaque job réclamé garde son entreprise ; aucun utilisateur ne réclame la file ni ne lit les jobs de l'autre entreprise. | `t1-isolation.test.ts` |
| Application (HTTP) | Pages Membres, Tableau de bord, Administration, SMTP appelées avec une vraie session : sans session → connexion ; l'admin d'Alpha ne voit aucune trace de Beta (texte visible et identifiant) et inversement ; un indice d'entreprise étranger est refusé ; analyste et sales agent n'ouvrent pas Membres ; personne hors administrateurs de la plateforme n'ouvre Administration ni SMTP. | `t1-isolation.test.ts` |
| T5 (changement d'entreprise) | Bascule Alpha → Beta puis lien profond d'Alpha : refusé ; indice falsifié, non-uuid, inexistant ou étranger : refusé ; **rôle rétrogradé, adhésion retirée ou entreprise suspendue en cours de session : l'accès tombe à la requête suivante**. | `t5-org-switch.test.ts` |

Couverture déjà existante (non répétée) : matrices RLS par rôle (`core-tables`, `invitations`, `audit-logs`, `jobs`, `quotas`, `smtp`…), 308 tests ; pgTAP 1314 ; tests de contexte tenant et d'actions côté application.

## 2. Rôles (critère §13-2) pour les rôles disponibles
Analyst n'accède ni à Membres ni aux écritures (RLS et page) ; Sales Agent n'accède pas à Membres ; Owner gère les membres ; Admin ne crée pas d'owner (RLS). « Sales Agent ne modifie pas l'intégration » et « Marketing Manager envoie seulement après approbation » : **non testables avant les modules Intégrations (J28) et Campagnes (J44)** ; ils restent planifiés à J59.

## 6. Verdict proposé
- **Aucun écart bloquant technique** : l'isolation est démontrée sur la RLS, l'API, la file de jobs et les pages ; la révocation en cours de session est prouvée.
- **Réserves** : écarts 1 à 4 (couverture à compléter, sans fuite constatée) et 5 à 7 (décisions de la responsable technique).
- **Recommandation : GO pour démarrer la Phase 2 (J16)**, à condition que les ADR de la phase soient relus et que l'écart 4 (CI) soit tranché. Sans cette validation, la règle du plan (« sans GO, la phase suivante ne démarre pas ») s'applique.
