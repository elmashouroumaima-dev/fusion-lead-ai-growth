1. Analyse de la spécification v1.0
La spécification fait de l'isolation des tenants le critère n°1 : tout le reste (CRM, canaux, campagnes, IA) n'a de valeur que si une entreprise A ne peut jamais lire ni modifier les données d'une entreprise B. Le plan s'aligne donc sur l'ordre imposé au §5 : isolation et adhésion → CRM et capture → boîte de réception → campagnes → IA → rapports → intégrations élargies.
1.1 Invariants non négociables
Ces règles sont reprises mot pour mot dans le fichier de règles de l'agent (§2) et vérifiées à chaque checkpoint.
1. Pas de n8n, ni dans le produit ni dans l'architecture ; tâches de fond dans les services applicatifs et un worker séparé (spec §1).
2. MCP n'est pas une file de jobs ni un moteur de permissions ; c'est une passerelle d'outils optionnelle, lecture seule d'abord (§1, §6).
3. organization_id uuid not null + index sur toute table tenant ; PK en UUID (§7). 4. RLS sur toute table exposée à la Data API, avec politiques séparées lecture/
écriture/suppression, USING et WITH CHECK , contrôle du rôle (§7.2, §11). 5. Jamais user_metadata pour une décision d'autorisation ; la source du rôle est
organization_members (§7.2). 6. Double contrôle : couche service + base de données ; le serveur ne fait jamais
confiance à un organization_id envoyé seul (§8, §11). 7. service_role uniquement côté serveur/worker, jamais dans le navigateur ni dans
une variable NEXT_PUBLIC_* (§6).

2. Fichier de règles permanent de l'agent (CLAUDE.md)
Ce fichier, placé à la racine du dépôt, est relu par l'agent à chaque session : il évite de répéter les contraintes dans chaque prompt. Copiez-le tel quel dans CLAUDE.md (ou AGENTS.md pour un autre agent), et placez la spécification dans docs/spec/ .
# CLAUDE.md — Fusion Leap AI Growth
## Rôle Tu es l'ingénieur·e logiciel senior qui développe Fusion Leap AI Growth, une plateforme SaaS multi-tenant. Tu travailles sous la direction de la responsable technique. Tu ne prends aucune décision d'architecture seul.
## Sources de vérité (par ordre de priorité) 1. docs/spec/Fusion-Leap-AI-Growth-Technical-Spec.md (spec v1.0, 3 nov 2026) 2. docs/adr/*.md (décisions validées qui précisent ou amendent la spec) 3. docs/plan/development-plan.md (plan validé au Jour 0) 4. docs/progress/journal.md (état réel du projet) Si le code et ces documents divergent, les documents gagnent. Si la spec est ambiguë ou muette : ARRÊTE-TOI et pose la question. N'invente jamais une table, un champ, un endpoint ou un fournisseur absent de la spec ou d'un ADR validé.
## Architecture imposée (spec §6) - apps/web : Next.js App Router (UI, API routes, webhooks, session) - apps/worker : worker Node séparé (jobs, sync, envois, agent runs) - packages/domain : types, validation zod, règles métier pures - packages/adapters : CRM, email, WhatsApp, Salla, AI (interface
connect / validate / send / receive / refresh / disconnect) - packages/permissions : RBAC + policy checks - supabase/migrations : schéma + RLS - docs : ADR, API, runbooks, journal
## Interdits absolus - n8n, sous quelque forme que ce soit.

pnpm lint && pnpm typecheck && pnpm test (+ pnpm test:rls si la base change). Tout doit être vert. 5. DOCUMENTER : mets à jour docs/ (API, ADR, runbook) et CHANGELOG.md. 6. RAPPORTER : termine par le rapport standard ci-dessous.
## Rapport standard de fin de tâche - Fait : liste des livrables, avec chemins de fichiers - Tests : commandes lancées + résultat (nombre de tests, échecs) - Écarts à la spec : aucun, ou liste justifiée - Questions ouvertes / blocages - Prochaine étape proposée
## Définition de « Terminé » - Critères de validation du jour atteints et démontrés - Lint, typecheck, tests unitaires, intégration et RLS verts - Migration réversible (fichier down ou procédure documentée) - Pas de TODO caché : tout reste à faire est listé dans le rapport - Documentation et journal mis à jour
