Guide complet du test réel (C3)

Fusion Leap AI Growth · Checkpoint C3 / Gate G3 · envoi, réception et arrêt sûrs sur le vrai Postmark et le vrai WhatsApp (Meta). Version du 18 novembre, avec l'écran de canaux (PR 64).

Règles de sécurité (à lire d'abord)
  • Ce test envoie de vrais messages : n'utiliser que vos adresses et vos numéros de test, jamais ceux d'un client.
  • Les jetons (Postmark, Meta), le secret de l'app Meta et les secrets de webhook ne se collent jamais dans une conversation, une capture d'écran ou une commande. Ils se saisissent dans les champs de l'application (écriture seule) ou dans des fichiers hors du dépôt (C:/secrets/).
  • Ne pas utiliser votre numéro WhatsApp personnel comme numéro d'envoi de l'application.
  • Après le test : révoquer ou remplacer tous les jetons et supprimer C:/secrets/. En cas de doute pendant un envoi : Operations → Stop all sending (test A1).

Partie 1 · Préparer la machine

1
Docker Desktop démarré (icône verte). Ouvrir Git Bash dans le dossier du projet.
2
Base locale neuve avec les comptes de démonstration : 
pnpm db:start
pnpm db:reset
Attendu : « Finished supabase db reset ». Les données de test précédentes sont effacées.
3
Fichier .env.local à la racine : SECRETS_MASTER_KEY doit déjà y être (sinon l'écran affiche « chiffrement non configuré »). Les deux autres variables viendront à la partie 4.
4
Deux terminaux séparés (Git Bash), gardés ouverts pendant tout le test : 
Terminal 2 :  pnpm dev
Terminal 3 :  pnpm worker:dev
Attendu : l'application répond sur http://localhost:3000. Se connecter par http://localhost:3000/en/login avec shared@seed.test (propriétaire d'Alpha), pas par l'adresse du tunnel.
Après chaque modification de .env.local : arrêter puis relancer les terminaux 2 et 3.

Partie 2 · Compte Postmark

Vous avez déjà un compte Postmark en mode test. Il manque l'adresse d'expéditeur réelle (le « toi@domaine.com » affiché par Postmark est un exemple, pas une adresse).

1
Sender Signature : Postmark → Sender Signatures → Add a sender signature → saisir une adresse que vous possédez (par exemple votre boîte Gmail ou celle de votre domaine) → Postmark envoie un e-mail de confirmation → cliquer le lien dedans.
Attendu : l'adresse est « Confirmed » (verte) chez Postmark.
2
Jeton du serveur : Postmark → Servers → votre serveur → API Tokens → copier le « Server API token ». Ne le collez nulle part sauf dans le champ de l'application (partie 3).
3
Mode test de Postmark : tant que le compte n'est pas approuvé, Postmark limite les destinataires (en général, aux adresses du même domaine que l'expéditeur) (à confirmer dans votre tableau de bord Postmark). Pour le test, utiliser comme destinataire une seconde adresse sur le même domaine, ou demander l'approbation du compte à Postmark.
Boîtes de test : l'adresse d'expéditeur (étape 1) et l'adresse de destination (votre « Testeur ») doivent être deux boîtes que vous pouvez ouvrir. Si une seule boîte est disponible : un envoi à soi-même fonctionne si Postmark l'accepte.

Partie 3 · Connecter l'e-mail dans l'application

1
Menu Integrations → carte « Connecter un e-mail (Postmark) » (en anglais : « Connect e-mail (Postmark) »).
2
Saisir l'adresse d'expéditeur confirmée (partie 2, étape 1) et le jeton du serveur Postmark, puis Connecter et vérifier.
Attendu : « Connexion vérifiée : le canal est actif. » ; une carte « E-mail » apparaît avec l'état Connectée, le canal Actif, « Jeton enregistré et chiffré ».
Si « Jeton refusé par Postmark » : mauvais jeton (prendre celui du serveur, pas celui du compte). Si « Postmark est indisponible » : réessayer. Si « Cette adresse ou ce compte est déjà connecté » : le domaine est déjà pris par une autre entreprise.
Point à confirmer pendant ce test : la vérification utilise la route GET /server de Postmark. C'est une hypothèse du code, jamais essayée sur un vrai compte : si la vérification échoue alors que le jeton est bon, notez le message exact et ne tentez rien d'autre (c'est un constat pour C3).
3
Secret du webhook e-mail (nécessaire pour les statuts « delivered » et les rebonds ; pas d'écran pour l'instant). Créer un secret et le mettre dans un fichier hors dépôt : 
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# copier la ligne affichée ; créer C:/secrets/webhook.json :
{"integration_id":"<identifiant de l'intégration e-mail>","secret":"<le secret>"}
pnpm test:call shared POST /api/integrations/webhook-secret --json-file C:/secrets/webhook.json
Attendu : HTTP 200 et { "replaced": true }.
Identifiant de l'intégration : pnpm test:call shared GET /api/integrations. Gardez le même secret pour l'URL du webhook (partie 4).
4
Contact de test et conversation (remplacer les valeurs entre chevrons ; wa_sender reste vide tant que WhatsApp n'est pas connecté) : 
docker exec -i supabase_db_fusion-leap psql -U postgres -v ON_ERROR_STOP=1 \
 -v mail_sender='<adresse d expéditeur du canal>' -v wa_sender='' \
 -v tester_name='Testeur C3' -v tester_email='<votre adresse de destination>' \
 -v tester_phone='' \
 < docs/testing/fixtures/c3-contact.sql
Attendu : « NOTICE: canal e-mail …, contact … » puis COMMIT. Dans Inbox : une conversation « Testeur C3 » avec un message reçu. Relancer le script avec la même adresse est refusé (« déjà exécuté »).

Partie 4 · Tests e-mail

Sans tunnel (E1, E3)

E1
Jeton chiffré, jamais relu. 
pnpm test:call shared GET /api/integrations
Attendu : has_secret: true ; aucune valeur de jeton dans la réponse ni sur l'écran.
E3
Réponse envoyée depuis la boîte de réception. Inbox → conversation « Testeur C3 » → écrire une réponse → Send reply. Le worker (terminal 3) l'envoie à Postmark ; ouvrir votre boîte de destination.
Attendu : « Reply queued » ; l'e-mail arrive, expéditeur = l'adresse confirmée, avec pied de page et lien de désabonnement ; la bulle passe à « Sent ».
« Failed » : lire le code (partie 6, tableau de dépannage). provider_rejected = Postmark refuse (adresse non confirmée, ou destinataire interdit en mode test).

Avec un tunnel (E4, E5, E6, E7)

Postmark ne peut pas appeler « localhost » : il faut une adresse publique HTTPS.

1
Dans un 4e terminal : 
cloudflared tunnel --url http://localhost:3000
(ou ngrok http 3000). Noter l'adresse https://xxxx.trycloudflare.com : elle change à chaque lancement.
2
Dans .env.local : 
SITE_URL=https://xxxx.trycloudflare.com
WHATSAPP_VERIFY_TOKEN=<16 à 200 caractères sans espace, inventés>
Puis relancer les terminaux 2 et 3. (SITE_URL sert au lien de désabonnement de chaque e-mail.)
3
Postmark → votre serveur → Webhooks → ajouter : 
https://<identifiant du compte>:<secret du webhook>@xxxx.trycloudflare.com/api/webhooks/email
Événements : Delivery, Bounce, Spam complaint. L'identifiant du compte est celui affiché sur la carte (« postmark-… ») ; le secret est celui de la partie 3, étape 3.
Attendu : le bouton de test de Postmark répond 200. 401 = mauvais identifiant ou secret.
E4
Statut « delivered ». Quelques secondes après un envoi (E3) : 
docker exec supabase_db_fusion-leap psql -U postgres -c "select status, provider_message_id is not null as id_fournisseur from public.messages where direction='outbound' order by created_at desc limit 3"
Attendu : « delivered » et un identifiant de fournisseur.
E5
Réponse du contact (si le flux Inbound de Postmark est configuré pour votre domaine). Répondre à l'e-mail depuis votre boîte.
Attendu : la réponse apparaît dans la conversation. Si Inbound n'est pas configuré : noter « non testé » (ce n'est pas un échec).
E6
Désabonnement. Dans l'e-mail reçu, cliquer le lien de désabonnement et confirmer. Puis demander un nouvel envoi : 
docker exec -i supabase_db_fusion-leap psql -U postgres -v ON_ERROR_STOP=1 \
 -v channel=email -v tester_email='<votre adresse de destination>' \
 -v body='Message après désabonnement' < docs/testing/fixtures/c3-approve.sql
Attendu : la page confirme ; le message est refusé par le worker (refused_suppressed ou refused_no_consent) ; rien n'arrive dans la boîte.
E7
Rebond ou plainte facultatif : si Postmark propose une adresse d'essai de rebond, l'utiliser pour un autre contact. Attendu : l'adresse est supprimée de la liste d'envoi. Sinon : « non testé ».

Partie 5 · WhatsApp

Choix du numéro (décision à prendre avant de commencer).
Option A (recommandée) : numéro de test de Meta. Meta for Developers → votre app → WhatsApp → API Setup : Meta fournit un numéro de test gratuit, un Phone number ID, un jeton temporaire et un WABA ID. Vous ajoutez votre téléphone comme destinataire autorisé (il reçoit un code). Aucun numéro réel n'est nécessaire. Le jeton temporaire expire en 24 h : à régénérer au besoin.
Option B : numéro réel via un prestataire (Kapso). Non supporté par le code actuel (adresse de l'API et signature des webhooks différentes) : cela demande un ADR validé par la responsable technique, puis du développement. À ne pas tenter pour C3.
Ne pas utiliser un numéro déjà inscrit sur WhatsApp (personnel ou Business app) : Meta le refuse (« numéro déjà enregistré »).
1
Récupérer dans Meta : Phone number ID, jeton d'accès, WABA ID, et le secret de l'application (Paramètres de l'app → De base → App secret → Afficher).
2
Application → Integrations → carte « Connecter un numéro WhatsApp » : coller Phone number ID, jeton d'accès, secret de l'app → Connecter et vérifier.
Attendu : « Connexion vérifiée : l'intégration est active ». Codes d'échec : provider_auth (jeton refusé), provider_account (numéro introuvable).
3
Canal WhatsApp : sur la carte WhatsApp, rubrique « Ajouter un numéro » : saisir le numéro de test de Meta au format +15550783881 → Ajouter → puis Vérifier la connexion. Le canal doit passer à Actif.
4
Webhook Meta (nécessite le tunnel de la partie 4) : Meta → WhatsApp → Configuration → Webhook : URL https://xxxx.trycloudflare.com/api/webhooks/whatsapp, jeton de vérification = WHATSAPP_VERIFY_TOKEN ; abonner le champ messages.
Attendu : Meta valide l'URL. 403 = jeton de vérification différent.
5
Ajouter le numéro WhatsApp à votre contact de test : relancer le script contact avec une nouvelle adresse de test, wa_sender='+15550783881' et tester_phone='<votre téléphone, E.164>'.

Tests WhatsApp

W1
Numéro connecté. Attendu : statut « Connectée / Actif » sur la page Integrations.
W2
Message entrant. Depuis votre téléphone, envoyer « Bonjour » au numéro de test Meta. Attendu : dans Inbox, la conversation WhatsApp contient votre message (contact reconnu par son numéro).
W3
Webhook rejoué : renvoyer l'événement depuis l'outil de test de Meta si possible. Attendu : toujours un seul message. Sinon : « couvert par T4 (automatique) ».
W4
Envoi dans la fenêtre de 24 h. La boîte de réception ne répond pas encore sur WhatsApp (écart connu n° 3) : le script fait approuver le message par le propriétaire. 
docker exec -i supabase_db_fusion-leap psql -U postgres -v ON_ERROR_STOP=1 \
 -v channel=whatsapp -v tester_email='<adresse du contact>' \
 -v body='Bonjour, test C3 WhatsApp.' < docs/testing/fixtures/c3-approve.sql
Attendu : le message arrive sur votre téléphone en quelques secondes.
W6
Statuts dans l'ordre (ouvrir le message sur le téléphone) : 
docker exec supabase_db_fusion-leap psql -U postgres -c "select status from public.messages where direction='outbound' order by created_at desc limit 1"
Attendu : accepted → sent → delivered → read, sans jamais reculer.
W5
Hors fenêtre : refus sans modèle. Vieillir le message reçu puis redemander un envoi (comme W4) : 
docker exec supabase_db_fusion-leap psql -U postgres -c "update public.messages set received_at = now() - interval '2 days' where direction='inbound' and conversation_id in (select c.id from public.conversations c join public.channels ch on ch.id=c.channel_id where ch.type='whatsapp')"
Attendu : refusé (refused_template_missing), rien n'est envoyé.
W7
Mot d'arrêt STOP. Depuis le téléphone, envoyer « STOP » au numéro de test, puis redemander un envoi (comme W4). Attendu : consentement retiré, envoi refusé par le worker, rien n'arrive.

Partie 6 · Arrêt d'urgence, fuites, clôture

A1
Tout s'arrête (le test le plus important). Préparer un contact valide (script contact, nouvelle adresse). Menu Operations → Stop all sending → confirmer. Demander un envoi.
Attendu : refus refused_organization_paused en moins d'un cycle du worker, rien n'est envoyé. « Resume sending » remet l'envoi en marche.
A2
Aucune fuite de secret ou de message dans les journaux et la base. Copier le contenu des terminaux 2 et 3 dans des fichiers hors dépôt, puis : 
# journaux : remplacer par le début de vos jetons / un texte de message ; AUCUNE ligne attendue
grep -c -E "<début du jeton>|<début du secret>|<texte d un message>" C:/secrets/journal-app.txt C:/secrets/journal-worker.txt
# base : tous les compteurs FUITES doivent valoir 0
docker exec -i supabase_db_fusion-leap psql -U postgres -A -t -F ' | ' < docs/testing/fixtures/c3-leak-scan.sql
Attendu : aucune ligne dans les journaux ; tous les compteurs « FUITES » à 0.

Après le test

  • Révoquer ou remplacer tous les jetons de test et le secret de webhook ; supprimer C:/secrets/.
  • Remplir la section 5 de docs/checkpoints/C3.md (OK / KO / non testé + une preuve sans donnée sensible).
  • Ne rien envoyer au dépôt qui contienne un jeton, une adresse réelle ou un numéro réel. pnpm db:reset efface les données de test.
